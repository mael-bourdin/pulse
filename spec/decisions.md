# Décisions d'architecture (ADR)

Format : décision, raison, alternative écartée. Toute nouvelle décision s'ajoute ici avec la date.

| # | Décision | Raison | Écarté |
|---|---|---|---|
| ADR-01 | **Rust** (serveur et simulateur), on repart de zéro | Langage compilé, performant, envie de l'apprendre. PULSE est un composant indépendant branché par contrats HTTP, donc le Java du SI n'impose rien (TECH §4.2) | Garder le TypeScript existant |
| ADR-02 | **Tauri 2** pour le desktop, sous forme de fenêtre qui charge l'URL de PULSE | Framework cross-platform Rust. Même origine que le web, donc la même session ; aucune logique dupliquée | Commandes Rust dans Tauri (pas de version web, droits côté client) ; interface embarquée (le cookie n'est pas envoyé depuis `tauri://localhost`) |
| ADR-03 | **Monolithe modulaire** + simulateur séparé | Simple à démontrer ; les microservices sont hors périmètre (CDC §6) | Un service par domaine |
| ADR-04 | `pulse-domain` **pur**, sans base ni HTTP | Règles testables sans infrastructure, faciles à expliquer | Logique dans les routes |
| ADR-05 | **Axum 0.8** | Le plus documenté de l'écosystème Tokio ; les extracteurs portent bien les contrôles d'accès | Actix Web, Rocket |
| ADR-06 | **React 19 + Vite + TypeScript** | L'équipe est à l'aise ; rapide | Leptos (personne ne le connaît, plus de 25 h) |
| ADR-07 | **REST `/api/v1`**, OpenAPI **généré** (utoipa) pour PULSE, **écrit à la main** pour l'auth | Une seule source de vérité par contrat ; le contrat d'auth est imposé de l'extérieur | OpenAPI de PULSE écrit à la main (double maintenance) |
| ADR-08 | Erreurs `{ code, message, details? }` | Même format que HAC-API-001 | RFC 9457 |
| ADR-09 | **404** pour la ressource d'un autre utilisateur, **403** pour un rôle insuffisant | Ne révèle pas l'existence d'une ressource ; refus visible pour l'admin (UX p.11) | 403 partout |
| ADR-10 | Session : **cookie httpOnly** qui contient le jeton opaque, `SameSite=Strict`, `Secure` en ligne ; `/me` appelé à **chaque** requête | Jeton invisible pour JavaScript ; REC-04 et REC-05 démontrables en direct ; aucune table de sessions | `sessionStorage` (XSS) ; cache de `/me` (session encore valide après `auth:down`) |
| ADR-11 | CSRF : `SameSite=Strict` + vérification de `Origin` + `Content-Type: application/json` obligatoire sur les écritures | Suffisant pour une API de même origine | Jeton CSRF |
| ADR-12 | Le front n'appelle **jamais** le simulateur ; seule l'API PULSE le fait | Un seul point de couplage (ACC-QUAL-02) | Appel direct depuis le front |
| ADR-13 | **PostgreSQL 16**, `sqlx` avec requêtes vérifiées à l'exécution + migrations | Base relationnelle réelle, déjà prévue par la trajectoire PULSE ; compile sans base disponible | Macros `query!` (base requise à la compilation) ; JSON ; SQLite |
| ADR-14 | Simulateur : utilisateurs dans un fichier JSON avec hachés **Argon2id**, jetons en mémoire (TTL 3600 s) | Fidèle au contrat, pas d'IAM (CDC §6) | Base de données pour le simulateur |
| ADR-15 | 503 : variable `AUTH_SIM_UNAVAILABLE` au démarrage **et** route de pilotage `POST /__control/availability` protégée par `AUTH_SIM_CONTROL_TOKEN`, hors de `/api/v1/auth` | Reproductible en local et en ligne, sans toucher au contrat | Fichier drapeau (inutilisable sur Railway) |
| ADR-16 | Limite de connexion **par IP** : 5 essais par minute | Ne révèle pas l'existence d'un compte (ACC-AUTH-05) | Limite par e-mail |
| ADR-17 | Hébergement **Railway** : 3 services (API publique, simulateur sur réseau privé, PostgreSQL). ~~Plan Free, Hobby le mois de la soutenance~~. *Complétée le 2026-11-25 par ADR-30 (deux environnements) et ADR-35 (tout gratuit : Railway Free pour les services, base sur Neon).* | Peu d'administration ; le simulateur n'est pas exposé sur Internet | VPS (administration), Render (mise en veille, base expirée), Netlify (pas de serveur Rust) |
| ADR-18 | Pas de Docker pour développer : tout tourne nativement sur les postes. *La partie « pas de CI » est remplacée par ADR-29 (2026-11-25).* | Choix de l'équipe ; « la conteneurisation industrielle » ne relève pas de V1 (TECH §5), Docker n'est qu'une orientation de la trajectoire (TECH §6) ; Railpack produit déjà une image sans Dockerfile | Docker Compose en local |
| ADR-19 | Le statut d'un défi est **saisi** par l'admin ; aucun statut n'est calculé à partir de la date du jour | Les données datent de février 2026 | Statut calculé |
| ADR-20 | Rejoindre un défi après l'avoir quitté **crée une nouvelle participation** | Historique conservé (PROD §6.4) | Réactiver l'ancienne |
| ADR-21 | Un objectif SUSPENDED peut être réactivé ; CLOSED est définitif | RG-GOAL-06 l'autorise | Pas de réactivation |
| ADR-22 | La progression d'un défi est **en lecture seule** | ACC-CHAL-08 demande seulement de la consulter | Saisie par l'utilisateur |
| ADR-23 | L'admin ne voit **rien** des participants, ni noms ni nombres | RG-ADM-06, confidentialité | Compteurs agrégés |
| ADR-24 | Contenus (SHOULD) faits **après** la validation F1–F6 | CDC §3.6, PROD §7 | Les faire en parallèle |
| ADR-25 | Usage de l'IA **déclaré simplement** dans L5 | CDC §9 | Ne pas le déclarer |
| ADR-26 | Les commits ne portent **aucune** ligne de co-auteur IA ; hook `commit-msg` | Choix de l'équipe ; l'historique reflète les auteurs réels | — |
| ADR-27 | FUNCTIONAL_ADMIN n'a **pas** accès à l'espace personnel (`/me/*` → 403), USER n'a pas accès à `/admin/*` | Espaces distincts (RG-AUTH-04/05, parcours UX : admin = P1 → P6) | Admin avec un espace personnel |
| ADR-28 | (2026-11-25) Git : `main` = production, `develop` = intégration et recette, branches courtes depuis `develop`. Squash vers `develop`, merge commit vers `main`, tag SemVer à chaque release ([workflow.md](workflow.md)) | Stratégie « simple » demandée (CDC §5.2) ; un environnement de recette distinct de celui de la démo ; un commit par exigence, lisible par le jury (L3) | GitFlow complet avec branches `release/` (trop lourd pour 21 h) ; tout sur `main` (aucun environnement de recette stable) |
| ADR-29 | (2026-11-25) CI GitHub Actions **bloquante** sur chaque PR et chaque push sur `develop` et `main` : jobs `rust`, `web`, `secrets`, `pr-title`, plus `e2e` vers `main`. `main` et `develop` protégées par des rulesets GitHub ([ci-cd.md](ci-cd.md)) | CDC §5.6 (« vérifications automatisées simples », absence de secrets, revues) ; dépôt public, donc minutes Actions et rulesets gratuits ; le 2026-11-23, `main` est restée rouge sans bloquer personne | `make check` seul (rien ne garantit qu'il a tourné) ; hook `pre-push` (contourné par `--no-verify`) |
| ADR-30 | (2026-11-25) Railway : deux environnements, `production` (déployé depuis `main`) et `staging` (depuis `develop`), chacun avec ses 3 services et sa base. Railway déploie lui-même depuis GitHub **après** la CI verte (« Wait for CI ») ; la CI ne déploie jamais. `production` est l'environnement de la démo et de la revue de version, sans vrais utilisateurs ; `staging` est l'« environnement de recette » au sens de HAC-API-001 §1 | Aucun pipeline de déploiement à écrire ni de jeton Railway dans GitHub : on reste hors de « la construction d'un pipeline CI/CD de mise en production », exclue de V1 (TECH §5, CDC §6) ; « isolation des environnements de développement et de recette » (API §1) | `railway up` lancé par Actions (jeton à protéger, pipeline à maintenir) ; environnements de PR (coût, build Rust lent) ; un seul environnement (recette sur la démo) |
| ADR-31 | (2026-11-25) Migrations lancées par la commande de pré-déploiement Railway (`pulse-api migrate`) ; une migration fusionnée dans `develop` n'est **jamais** modifiée ; après `v0.2.0`, migrations additives seulement | Une migration en échec annule le déploiement et l'ancienne version reste en ligne ; sqlx refuse une migration déjà appliquée dont le contenu a changé | Migrations au démarrage de l'API (le schéma et le démarrage se mélangent) ; modifier une migration existante (casse `staging` et `production`) |
| ADR-32 | (2026-11-25) Aucune sauvegarde de base : restaurer = `make seed-remote` | Données 100 % synthétiques et rechargeables (CDC §4.5) | Sauvegardes Railway |
| ADR-33 | (2026-11-25) Trello passe à 6 colonnes (« En recette » entre « En revue » et « Terminé ») et chaque carte porte une priorité **MoSCoW** (MUST, SHOULD, COULD, WON'T). Remplace D-15 sur ces points | Une carte n'est finie qu'une fois vérifiée sur `staging` par un autre membre que l'auteur ; les WON'T gardent visibles les arbitrages pour L2 et L7 | Garder 5 colonnes et MUST/SHOULD seuls |
| ADR-34 | (2026-11-25) Commits en convention **Angular**, titre de PR vérifié par la CI ; versions, changelog, tags et Releases GitHub produits par **release-please** à partir de ces commits | Conventions communes (CDC §4.3), historique Git exploitable (L3), revue de version tracée (CDC §8, API §9). release-please n'écrit que le changelog et les tags et ne déploie rien : TECH §5 est respecté | Tags et notes à la main (numéros arbitraires, oublis) ; semantic-release (publie à chaque fusion, sans PR à relire) |
| ADR-35 | (2026-11-25) Hébergement **gratuit** : `pulse-api` et `auth-simulator` sur Railway Free, PostgreSQL 16 sur **Neon Free** (un projet par environnement). Mise en veille acceptée, chauffe avant chaque démo ([ci-cd.md](ci-cd.md) → Plan et coût) | Règle d'équipe : 0 € ; Railway Free n'autorise qu'un volume par projet, donc une seule base Railway ; Neon est gratuit sans limite de durée ni carte, en PostgreSQL 16, et accepte toute l'équipe | Railway Hobby (payant) ; Railway Postgres (une seule base) ; Supabase (pause après 7 jours) ; Render (base supprimée après 30 jours) ; auto-hébergement Oracle + Dokploy (carte bancaire, administration), gardé en dernier repli |
